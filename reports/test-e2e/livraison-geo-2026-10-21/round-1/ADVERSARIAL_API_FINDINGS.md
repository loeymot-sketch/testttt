# Livraison Le Cayenne — attaque adversariale API (équipe 2, round 1)

Date : 2026-10-21. Cible : serveur LOCAL `http://127.0.0.1:8767`, base `foodking_e2e` (jamais la production).
Arbre servi : HEAD `2ada1463a` + modifications non commitées de l'équipe 1 (`RouteServiceProvider.php`, `routes/api.php` : limiteurs nommés des 4 routes publiques `delivery/*`).
Méthode : requêtes HTTP réelles (scripts Python/curl dans le scratchpad de session), relecture en base via tinker, aucune écriture dans le dépôt (hors ce rapport). Données créées préfixées `TEST-ADV` (clients 830/831, livreurs 832/833, caissier 842, commandes ~7893-7951, arrêts 20-60).
Règle CLAUDE.md §3ter : tout P0/P1 ci-dessous cite un `file:line` relu ET une reproduction exécutée (deux fois pour F-ADV-1).

Définition : P0 = prix faux / fuite de données / fiscal / écriture non autorisée ; P1 = défaut fonctionnel bloquant le service ; P2 = défaut réel, contournable ou conditionnel ; P3 = hygiène. **P0/P1 bloquent la livraison.**

## Verdict

**1 P0 bloquant (F-ADV-1)** — une livraison demandée avec `payment_method=5` est scellée PAYÉE (numéro fiscal alloué) au départ du livreur sans qu'aucun paiement n'existe, et l'écran livreur affiche « Déjà payé 0 € ». Aucun autre P0/P1 trouvé : prix, adresse, IDOR, fichiers, créneaux, géocodage fail-closed, idempotence ont tenu.
`php artisan fiscal:verify-chain --all` : CHAIN OK sur 7 branches avant ET après mes manipulations ; numéros fiscaux de mes 17 ventes contigus (2860-2878), 0 doublon. (Des trous plus anciens existent sur la branche 1 — 2505→2509, 2679→2690, … 2756→2782 — hérités de suppressions de commandes de test d'autres sessions, antérieurs à mes manipulations.)

## Défenses prouvées (attaques ÉCHOUÉES)

Prix / adresse
- `delivery_charge` forgé (0, -5, "abc", 1e308), `delivery_distance_km`, `latitude/longitude/lat/lng`, `city`, `postal_code` envoyés avec la commande web, la commande caisse (devis + création) : toujours remplacés par le prix serveur de l'adresse enregistrée (3,90 / 5,90…), totaux corrects en base.
- Commande caisse : charge forgée seulement au `store`, ou adresse changée entre devis et création -> 409 « Order quote intent mismatch » ; livraison sans client / client de passage / compte équipe / client d'un autre -> 422 « Adresse invalide ».
- `address_id` d'un autre client (web) -> 422/403 ; inexistant, 0, tableau, « 1e0 », « 28.9 » -> refus (« 28.9 » ne se détourne pas vers l'adresse 28) ; commande à emporter avec l'adresse d'un autre -> 403 « OrderAddress IDOR refused ».
- Création/modification d'adresse : `city`/`postal_code`/`latitude`/`longitude`/`geocode_status` envoyés par le client ignorés (adresse Paris 75001 forgée -> enregistrée Hénin-Beaumont 62110 avec coordonnées BAN) ; PUT avec coordonnées du restaurant sur une adresse d'Oignies -> coordonnées BAN réécrites, commande à 5,90 € ; PUT avec texte absurde -> 422 sans écraser l'ancienne adresse.
- Barème : bornes 5,00/8,00/10,00 km inclusives et 5,0000001/8,0000001/10,0000001 km au palier suivant ou refus (`DeliveryTariff`, 34 cas : chaînes, « 5,0 », NaN, INF, négatif, null, tableau -> `invalid`/refus, jamais un prix).
- Homonymes : seule commune 62110 = Hénin-Beaumont (geo.api.gouv.fr) ; « HENIN BEAUMONT », tiret demi-cadratin, espaces, casse -> forfait maison ; tiret insécable U+2011 ou accent décomposé (NFD) -> pas de forfait maison (surfacturation, jamais sous-facturation) ; « Hénin-Beaumont » seul -> refusé ; « Lens » + 62110 -> point BAN réel.
- Entrées malveillantes `q` (apostrophe/SQL, `\0`, emoji, 200/201 car., `{{7*7}}`, `${jndi:}`, CRLF, `../`, RLO, `q[]`, `&limit=500&lat=0`) : jamais de 500, paramètres BAN non injectables (URL-encodés), longueur bornée (422).
- Panne / réponses piégées de la BAN (serveur factice local : 500, HTML, vide, sans `features`, géométrie nulle, score 0,2, délai 8 s, port fermé) -> `GeocodeUnavailableException`, jamais un prix (fail-closed). Coordonnées hors plage ou lat/lon inversés -> distance énorme -> refus.
- Cache de géocodage : clé = sha1 du texte replié (`AddressGeocoder.php`) ; non empoisonnable par un client sans contrôle de la BAN ; une panne n'est pas mise en cache.

Autorisations
- Sans jeton : 401 sur `delivery-run` (index, depart, arrive, deliver, photo). Jeton sans capacité (`nothing`) et client : 0 donnée (liste vide), `depart/arrive/deliver` refusés, photo 403.
- Livreur B sur l'arrêt/la commande du livreur A : `depart` 404, `arrive/deliver` 403 « ne vous est pas attribuée », photo 403, ancienne route `delivery-boy-order` change-status/show 403. Client B/A : photo 403, lecture/modification de l'adresse ou de la commande d'un autre -> 403.
- Client, livreur, jeton sans capacité sur `GET/POST /api/admin/pos-delivery/*` (status, toggle, board, assign, lookup, customer, address, suggest, quote) et sur `/api/admin/pos`, `online-order`, `delivery-boy/*`, `select-delivery-boy` : 403 partout (les POST client sont arrêtés plus tôt par le garde d'idempotence, 422).
- `pos-delivery/customer` ne détourne pas un compte (e-mail/nom/téléphone +33 d'un client existant inchangés, aucune écrasement) ; e-mail déjà pris -> non rattaché.
- `waves/assign` : compte non livreur (admin 1, client 837) -> 422 ; types invalides -> 422 ; tournée absente -> `assigned:0`.
- XSS : `apartment`, nom, téléphone, adresse échappés par `esc()` dans `/livreur`.

Machine d'états / fichiers / créneaux
- Remise ou arrivée avant départ -> 409 ; remise deux fois -> 409 « déjà remise » ; rejouer avec la même clé -> même réponse sans second effet ; même clé + corps différent -> 409 ; départ/arrivée/remise sans `X-Idempotency-Key` -> 422 ; commande web rejouée 4 fois en parallèle avec une clé -> 1 seule commande.

- Types invalides sur `customer_id`, `delivery_boy_id`, `wave_at`, `stop` (abc, -1, 1e3, 999…9, tableaux) -> 422/404, jamais de 500.
- `payment_method` omis -> traité comme espèces (pas de paiement fantôme) ; commande table (QR) de type livraison -> 422.

Fiscal
- Livraison espèces livrée : n° fiscal alloué à la remise, audit d'escrow présent (1 ligne), chaîne `fiscal:verify-chain --all` verte avant/après (7 branches), séquence contiguë sur mes ventes, 0 doublon. (F-ADV-1 est l'exception : n° alloué sans paiement.)

Débit

## Recommandations (lecture seule — rien n'a été modifié)
1. F-ADV-1 : limiter `payment_method` des livraisons web à {1, 4} (ou refuser l'acceptation / le passage PAID tant qu'aucun paiement n'existe pour un mode non espèces) ; faire afficher au livreur le mode réel même après le passage PAID ; test de non-régression avec `payment_method=5`.
2. F-ADV-2 : borner `collected_cents` (≤ montant dû, ≤ 2 147 483 647) et envelopper transition + save de l'arrêt dans une transaction (ou écrire l'arrêt avant, via `DB::transaction`).
3. F-ADV-3 : ajouter `idempotency.branch` basé sur l'arrêt (ou résoudre la branche du livreur depuis `delivery_stops.branch_id`) ; contrôler `users.branch_id` du livreur de production.
4. F-ADV-4 : limiteurs nommés (ou préfixe) pour `pos-delivery/*`, comme fait pour les routes publiques.
5. F-ADV-8 : lire en production `free_delivery_above` ; le poser explicitement à 0 si le barème propriétaire doit s'appliquer sans exception.
