FOOTNOTE A — Why audit_logs and fiscal_sequence_no did not grow:
  All 5 F.2 stress invocations were rejected at middleware or FormRequest BEFORE
  reaching the OrderService / FiscalSequenceService. The kiosk run was 429-blocked
  by the kiosk-orders rate limiter (5/min prod default; 60/min local — exhausted
  by 100-burst on a single freshly-provisioned user+IP). The POS runs hit progressive
  422/401 because E2EStressCommand.minimalPosOrderPayload() is documented as
  "best-effort" and was missing required fields (is_advance_order, source,
  pos_payment_method, pos_received_amount AND the quote-token pair that PosController
  requires for the POST /api/admin/pos endpoint). One scope-minimal repair PR-ready
  (added 4 fields) but the quote-token path requires deeper refactor — V1.0.2 backlog.

FOOTNOTE B — Where the +6 orders / +19 outbox / +12 stale outbox came from:
  Parallel agents F.10 / F.11 / F.1 were running concurrently (Phase F dispatched
  ~8 agents in parallel per the prompt). Their refund + Z-close + rate-limit-UX
  flows wrote orders + DomainEvents + AuditLogs during the same 5-min window.
  F.2 created 0 orders directly — its delta to system state is conceptually 0.

FOOTNOTE C — stress_users_left=26:

  — they may be referenced by created orders for audit reasons." Token deletion
  happens; user rows persist. Each F.2 invocation provisioned 1 cashier and

  ~2-3 users per run × 5 = ~10-15. The 26 figure includes leftovers from
  earlier sessions' stress tests. Not a leak — design choice for NF525 audit

CUMULATIVE-PRESSURE OBSERVATIONS (THE OWNER'S METAPHOR SIGNAL)
------------------------------------------------------------------

P1. RATE LIMITER HOLDS UNDER BURST (positive finding):
    The kiosk-orders bucket (`Limit::perMinute(60)->by('kiosk:<user>|<ip>')`,
    `app/Providers/RouteServiceProvider.php:60-71`) saturated within ~2 seconds
    of a 100-request burst from a single user+IP and 100% rejected subsequent
    requests with HTTP 429 + canned "Trop de commandes. Veuillez patienter."
    Recovery requires bucket window roll-over (60s). This is the bouncer
    working AS DESIGNED — no production exposure here. A real-world legitimate
    kiosk burst pattern (cashier rushing 10 orders in 1 minute) sits comfortably
    inside the 60/min cap. The 100/sec burst tested here corresponds to a
    pathological bot — and was 100% throttled.

P2. SERVER PROCESS MEMORY DID NOT LEAK:
    14 RSS samples of the artisan-serve PHP worker (PID 94396) over 5 minutes
    of attempted load: baseline 51040 KB → in-burst peak 56352 KB → settled
    final 48448 KB. **Net change: -2.5 MB.** Garbage collection released memory
    AFTER the burst window closed. Two-key takeaway:
      (a) +5 MB peak during 100-request burst is bounded and reasonable
      (b) The fact that final < baseline means heap was reclaimed — no
          steady-state listener/cache leak signature
    Caveat: PHP's built-in dev server uses single-process+single-request
    serving. Production php-fpm would show different worker-level dynamics
    (workers spawn/die) — different test apparatus required for prod parity.

P3. OUTBOX DELTA — NOT F.2'S FAULT but worth noting:
    Pre-existing 751 stale events (the persistent dev-box backlog noted in
    CLAUDE.md as ~742, now grown). Parallel agents added +12 more during
    the window. Independent of soak. The lack of a worker drain on this
    dev box is documented (C8 finding per CLAUDE.md). Production cutover
    requires `queue:work` daemon.

P4. NO 5XX OBSERVED:
    Across 5 soak attempts × ~120 total requests, status breakdown:
      429: 100 (kiosk rate-limit)
      422: 118 (POS validation, decreasing as fixes were applied)
      401: 3 (POS quote_token requirement)
    Zero 500-class. Zero "connection refused". Zero timeouts. The system
    rejected gracefully at every gate it owns. No internal server explosion
    under pressure.

P5. NO CACHE::LOCK CONTENTION SIGNAL:
    Because no fiscal_sequence_no allocations happened during the soak (all
    requests rejected at validation), the Cache::lock 5s + DB FOR UPDATE
    triple-defence WAS NOT EXERCISED. This means F.2 cannot attest to that
