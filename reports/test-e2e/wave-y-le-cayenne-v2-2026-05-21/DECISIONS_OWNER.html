DÉCISION #2 — F2 P1 NF525 risk

💰 API Pricing renvoie 422 — risque que les prix affichés ≠ prix backend

📍 Symptôme technique : Quand le client choisit certaines compositions dans le wizard (probablement sauces multiples), le serveur refuse la requête de prix avec un code 422. La borne a un "plan B" local : elle calcule elle-même le prix et affiche "Tarif rafraîchi localement".
⚠️ Risque NF525 : Si le calcul local diverge du backend (par exemple +0,10€ d'erreur), le ticket fiscal sera faux. Loi française = prison possible si chain audit comptable cassée.
🍽️ Analogie : Imagine le caissier qui devrait toujours utiliser la calculette officielle (backend) pour donner le prix. Mais quand la calculette plante, il utilise sa tête à la place (calcul local). Tant qu'il a la même formule, OK. Mais si jamais sa tête se trompe de 10 centimes, le ticket imprimé sera illégal.
🔍 Option A — Investiguer + fix le 422 RECOMMANDÉ

Reproduire le 422 avec curl, voir quel payload le backend refuse, fixer le bug serveur.

  • Élimine le risque NF525 à la source
  • Le local fallback redevient un VRAI plan B
  • Hors frozen-zone (controller, pas service)
  • 1-3h d'investigation selon root cause

⏱️ Effort : 1-3h selon le bug trouvé

📚 Glossaire — Concepts mentionnés

🛂 Axios interceptor
Un "agent de douane" qui contrôle chaque message entre la borne et le serveur. Permet de gérer auto-retry, refresh token, dedup. Standard SaaS.
🔒 Frozen-zone
Liste de fichiers sacrés (wizard kiosk, payment component, services NF525). Toute modification = procédure LOCK + validation owner. Pourquoi : ces fichiers sont production-validated, trop critiques pour casser.
⚖️ NF525
Loi française obligatoire pour caisses enregistreuses. Impose : prix calculé backend (jamais frontend), tickets immuables, chain HMAC inviolable, 6 ans de rétention. Violation = prison + amendes lourdes.
📦 Bundle / npm run dev
La borne et la caisse fonctionnent en JavaScript "compilé" (= bundle). Quand on modifie le code source Vue, il faut recompiler avec npm run dev pour que la borne voie les changements.
🔄 MenuSnapshot bump
Numéro de version du menu. Quand on change un prix, on "bump" (+1) ce numéro. La borne voit le nouveau numéro → recharge le menu. Sans bump, la borne peut garder l'ancien menu en cache.
🌐 CORS
Règle de sécurité navigateur. Si APP_URL = "localhost" mais accès via "127.0.0.1", le navigateur refuse silencieusement certaines requêtes. Fixé via config/cors.php dans cette Wave Y.
🎯 P0 / P1 / P2 / P3
P0 = bug critique, bloque production.
P1 = bug visible client, à fixer avant lancement.
P2 = UX polish, post-lancement.
P3 = cosmétique pur, optionnel.
🔁 Round / Convergence
Cycle complet capture → audit → fix → re-capture. Convergence = 2 rounds consécutifs avec 0 bug. Garantit pas de régression cachée.
👯 GStack agent / Adversarial agent
GStack = agent qui CAPTURE et FIX. Adversarial = agent qui CRITIQUE le travail du GStack pour trouver ce qu'il a manqué. Méthodologie "défense en profondeur".

❓ Autres questions techniques user-friendly

Pourquoi "bundle stale" empêche les fixes Wave C de marcher ?
J'ai modifié le code source Vue, mais le navigateur lit la version compilée. Sans npm run dev, ton browser sert l'ancienne version. C'est comme imprimer un menu, modifier le PDF, puis donner l'ancien menu papier au serveur — il sert l'ancien menu.
Pourquoi le bug A-001 affectait toutes les 11 catégories ?
Le code backend triait les items avec une syntaxe invalide (sortBy([fn1, fn2])). Laravel l'a silencieusement interprété mal → tri broken partout. Ton problème "Sandwich Cayenne lands Boissons" était le symptôme visible du bug. Le fix corrige toutes les catégories en bonus.
Pourquoi tu m'as proposé un Axios interceptor au lieu de toucher KioskAppComponent.vue ?
KioskAppComponent.vue est dans ta zone "frozen" (sacrée). Toucher = paperasse LOCK + risque casser ton wizard parfait. L'interceptor agit DEHORS de cette zone — même résultat, zéro risque. C'est exactement la philosophie de tes frozen-zones : on protège le cœur, on travaille à la périphérie.
Le local pricing fallback (F2) c'est dangereux comment exactement ?
Imagine : le client commande Tacos avec 3 sauces. Backend dit "8,90€". Backend plante → frontend calcule "8,40€" (oublie 0,50€ de sauce extra). Le ticket NF525 imprime 8,40€. Tu rends 0,50€ moins de TVA à l'État. Audit fiscal = écart inexplicable = sanctions. C'est pour ça F2 est urgent même si "marche en apparence".
Pourquoi tu insistes tellement sur frozen-zone ?
Parce que tu m'as dit "le wizard popup POS est parfait, n'y touche pas". Ces fichiers sont ton capital produit. Si je casse le wizard en voulant fix un bug à côté, tu perds des mois de polish. Frozen-zone = "Claude, mains-off, sauf gate explicite". C'est ta sécurité face à moi.
Pourquoi mes anciens fichiers (sauce_*.png, viande_*.png) sont encore là ?
L'auto-classifier Claude a bloqué mon archivage en masse (mesure de sécurité — éviter destruction accidentelle). Ces fichiers sont maintenant orphelins (plus référencés dans menu_images.php). Pour les bouger, tu peux dire "archive les anciennes images sauce_/viande_/supplement_" et je le fais avec ton OK explicite.
Pourquoi "MenuSnapshot::bump" si on a déjà cache:clear ?
cache:clear = vider le cache du serveur. MenuSnapshot::bump = dire aux navigateurs clients "votre menu est obsolète, retéléchargez". Les 2 sont nécessaires. Un seul = un sous-ensemble des clients voit l'ancien menu.
C'est quoi composition_snapshot ?
Quand un client passe commande, on fige TOUS les détails (prix, sauces, viande, suppléments) dans une "photo JSON" au moment T. Cette photo est immuable. Si tu changes le prix Tacos à 7,90€ demain, les commandes d'aujourd'hui restent à 6,90€. C'est NF525 — pas de réécriture historique.
