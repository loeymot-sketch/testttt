**Date** : 2026-04-16
**Branche** : `refactor/staff-only-v1`
**Périmètre** : technique + structure + parcours (caissier + borne + customer) A→Z

## 🎯 TL;DR — Verdict global en 10 lignes

1. **Stack solide, architecture propre** : Laravel 9 + Vue 3 SPA + Sanctum + Spatie Permission + Outbox Pattern + Echo/Pusher. Séparation couches claire (Services, Events, Jobs, Listeners).
2. **V1 staff-only + kiosk autonome** livré et E2E-testé (9/9 Playwright + 5/5 PHPUnit). Rollback en <10s via flag.
3. **Temps réel enfin fonctionnel** depuis V5 (2 bugs critiques : bootstrap jamais importé + Vite vs Mix). Outbox → Pusher → `branch.{id}` → tous clients.
4. **Parcours caissier** : login → `/admin/pos` → wizard modal → `POST /api/admin/pos` → `Order status=ACCEPT, payment=PAID` → KDS instantané. Idempotency-key en place. Serveur recompute prix (SSOT).
5. **Parcours borne** : boot → auto-login machine (`kiosk:order` token) → idle (vidéo) → categories → wizard → cart → upsell/loyalty → payment (card/cash/TR) → waiting (polling 15s + Echo) → ready → auto reset.
6. **Écart critique V4.1** : le wizard borne est un stepper Vue multi-step, PAS encore la version POS single-page avec emojis/compteurs/crudités pré-sélectionnées demandée par l'user. Flag `KIOSK_USE_POS_WIZARD` prêt, wrapper en place, **réécriture à exécuter**.
7. **Écarts mineurs détectés** : `kioskDefaultLocale` injecté mais ignoré (i18n hardcode `fr`), `kiosk.confirmation` route unreachable (payment→waiting only, jamais confirmation), `KIOSK_USE_POS_WIZARD` flag s'applique uniquement à la route `/kiosk/wizard/:id` mais pas au wizard overlay déclenché depuis `kiosk.categories`.
8. **Dette tech réelle** : 3 god-files (OrderService 1693 L, PosComponent 1862 L, pos-wizard.js 5763 L), notifications SendOrder* synchrones (bloquent HTTP), `HasDomainEvents::recordDomainEvent` trait défini mais jamais appelé, rôle "Stuff" (typo) en seeder.
9. **Risques prod** : `QUEUE_CONNECTION=sync` par défaut, `CACHE_DRIVER=file` (Cache::lock non-optimal multi-workers), Debugbar peut fuiter en prod si `APP_DEBUG=true`, certains endpoints kiosk (`kiosk-event`) ne vérifient pas `tokenCan('kiosk:order')`.
10. **Production-ready à 90%** : V1 livrable après V4.1 (wizard unifié) + rotation password kiosk + durcissement QUEUE/CACHE prod + audit final 4 gates humaines.

## 2️⃣ Modèle de sécurité

### 2.1 Stratégie d'authentification

```
┌──────────────────────────────────────────────────────────────┐
│  CLIENT HTTP  (SPA / Kiosk / Mobile futur)                   │
│  Headers:                                                    │
│   • x-api-key: <MIX_API_KEY>       (gate API obligatoire)    │
│   • Authorization: Bearer <token>  (si authentifié)          │
└─────────┬────────────────────────────────────────────────────┘
          │
          ▼
┌──────────────────────────────────────────────────────────────┐
│  Laravel middleware pipeline                                 │
│  ┌───────────────────────────────────────────────────────┐   │
│  │ 1. ApiKeyMiddleware (x-api-key === config.api_key)   │   │
│  │ 2. Sanctum auth:sanctum (résout Bearer → $user)      │   │
│  │ 3. Spatie permission:<resource> (RBAC)               │   │
│  │ 4. Rate limiter nommé (api/kiosk-orders/admin-*)     │   │
│  │ 5. CorrelationIdMiddleware (X-Correlation-ID)        │   │
│  └───────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 Rate limiters (tous dans `app/Providers/RouteServiceProvider.php`)

| Nom | Limite | Clé | Usage |
|-----|--------|-----|-------|
| `api` | 120/min | user_id ou IP | Toutes routes `/api/*` |
| `login-lockout` | 10 / 10min | `email\|ip` | Login, kiosk-login, signup-otp |
| `kiosk-orders` | `config('kiosk.order_rate_limit', 5)`/min | IP | `POST /api/frontend/order` depuis borne |
| `admin-mutation` | 30/min | user_id | Routes admin mutation |
| `pos-order-create` | 60/min | user_id | Création commande POS |
| `pos-order-update` | 120/min | user_id | Update commande POS |

⚠️ **Écart mineur** : `kiosk-login` partage le bucket `login-lockout` avec le login staff — après login failures répétés d'un POS operator, la borne même IP peut être bloquée.

### 2.3 Modèle de tokens Sanctum

| Type | Ability | Durée | Usage |
|------|---------|-------|-------|
| Staff admin | toutes (pas de scope restrictif) | `config('sanctum.expiration', 480)` min | Web SPA admin |
| Kiosk machine | `kiosk:order` **uniquement** | 480 min | Borne — limite à commande, pas admin |

Le scope `kiosk:order` est vérifié :
- **Channel auth** `branch.{branchId}` : `tokenCan('kiosk:order')` → vérifie que `KioskMachine.branch_id === branchId` (sinon escalade possible vers toutes les branches) — `routes/channels.php:25-38`
- **OrderRequest** : impose `order_type=takeaway` pour les tokens kiosk — `app/Http/Requests/OrderRequest.php:65-71`

⚠️ **Écart** : `POST /api/frontend/kiosk-event` n'appelle **pas** `tokenCan('kiosk:order')` — seulement `auth:sanctum`. Un user staff lambda pourrait poster des événements kiosk.

### 2.4 Rôles & permissions seeded

```
Admin, Customer, Delivery Boy, Waiter, Chef,
Branch Manager, POS Operator, Stuff  ⚠️ typo (doit être "Staff")
```

Chaque rôle a `landing_url` (admin dashboard) et est rattaché à un `branch_id` pour les non-admins.

### 4.2 Points forts

- Soft-deletes sur `users`, `orders`, `order_items`, `branches`, `item_categories`
- Index composites pour performance : `order_items.order_id`, `order_status_transitions(order_id, order_type, occurred_at)`
- Contraintes FK + `branch_id` scoping pour isolation multi-tenant
- Audit trail complet : `order_status_transitions` + `action_logs` + `deletion_log`

### 4.3 Points faibles

- ⚠️ Le modèle `FrontendOrder` alias `protected $table = "orders"` — ce qui ajoute une confusion (deux modèles sur la même table, risque de divergence scope/observer)
- ⚠️ Pas d'index sur `orders.status` + `orders.branch_id` combiné — KDS filter `status IN (1,2,3)` + `branch_id=X` pourrait scanner
- ⚠️ Pas de `transactions` row créée pour les paiements POS cash/card dans `posOrderStore` — traçabilité financière incomplète

### Edge cases POS

| Scénario | Gestion |
|----------|---------|
| Double submit | `X-Idempotency-Key` header + DB column (`OrderService:548-555`) |
| Prix forgé côté client | Serveur recalcule depuis items/variations/extras en DB (rejeté si item cross-injection) |

| Scénario | Gestion | Statut |
|----------|---------|--------|
| Offline | Queue IndexedDB, orderRef `offline_*`, sync au retour | ✅ robuste |

| Session expirée (token 480 min) | Axios 401 → re-login via kioskAutoLogin | ✅ (sauf maintenance mode) |

## 8️⃣ Domain Events & Outbox Pattern

### 8.1 Flux

```
                          ┌──────────────────┐
                          │  Order mutation  │  (POS or Kiosk checkout)
                          │  OrderService    │
                          └────────┬─────────┘
                                   │
                    event(new OrderCreated($order))
                                   │
         ┌─────────────────────────┼──────────────────────────┐
         │                         │                          │
         ▼                         ▼                          ▼
  ┌──────────────┐       ┌──────────────────┐       ┌──────────────────┐
  │ FCM listener │       │ Outbox listener  │       │ Stock listener   │
  │ (synchrone)  │       │ (DB.afterCommit) │       │ (synchrone)      │
  └──────┬───────┘       └────────┬─────────┘       └──────────────────┘
         │                        │
         │                   INSERT domain_events
         │                   (channel, payload,
         │                    broadcast_as, ...)
         │                        │
         │                  afterCommit: dispatch
         │                   DispatchDomainEventsJob
         ▼                        ▼
   SendFcmJob             ┌──────────────────────┐
   (queue=default)        │ Queue worker (high)  │
                          │ tries=5, backoff     │
                          │ [1,5,30,300]         │
                          └──────────┬───────────┘
                                     │
                                     ▼
                          ┌──────────────────────┐
                          │ Pusher::trigger()    │
                          │ private-branch.{id}  │
                          └──────────┬───────────┘
                                     │
                                     ▼
                               SOKETI relay
                                     │
                                     ▼
                   Tous clients Echo sur branch.{id}
                   (KDS, OSS, POS, Kiosk)
```

### 8.2 Événements broadcasted

| Class (`app/Events/*`) | Listener outbox | Channel | broadcast_as |
|------------------------|-----------------|---------|--------------|
| `OrderCreated` | `PersistOrderCreatedToOutbox` | `private-branch.{id}` | `OrderCreated` |
| `OrderStatusChanged` | `PersistOrderStatusChangedToOutbox` | `private-branch.{id}` | `OrderStatusChanged` |
| `ItemAvailabilityChanged` | `PersistItemAvailabilityChangedToOutbox` | `private-branch.{id}` | `ItemAvailabilityChanged` |

Contrat payload (`resources/js/services/eventContract.js`) :
```json
{
  "version": 1,
  "type": "order.created",
  "aggregate_id": 42,
  "branch_id": 1,
  "occurred_at": "2026-04-16T18:30:00Z",
  "correlation_id": "uuid-...",
  "payload": { ... }
}
```

### 8.3 Replay / récupération

- **`php artisan outbox:rescue`** : relance les rows `dispatched_at=NULL` + `attempts<5` et stales >5 min
- **`php artisan outbox:retry-failed`** : reset les rows en `failed` scope

### 8.4 ⚠️ Écart observé

Le trait `HasDomainEvents` (`app/Traits/HasDomainEvents.php`) expose `recordDomainEvent()` pour que les modèles enregistrent des events à eux-mêmes. **Aucun appelant en production** : outbox alimenté uniquement via listeners. Le trait est wired sur `Order` + `FrontendOrder` mais dormant. Soit l'intégrer (ex: transitions via `Order::transitionTo($newStatus)` qui enregistre l'event), soit le supprimer.

## 1️⃣4️⃣ Verdict final

### Ce qui marche 👍

1. **Architecture Laravel 9 / Vue 3 / Outbox / Echo** très propre, avec séparation claire des couches.
2. **Sécurité** : Sanctum + abilities + x-api-key + rate limits + channel auth scopée : modèle à la hauteur.
3. **Staff-only + Kiosk autonome** : livré, testé (9/9 E2E + 5/5 PHPUnit), rollback flag-driven.
4. **Realtime** : enfin vraiment actif après V5 (avant c'était dead code pendant des mois sans le savoir).
5. **Idempotency**, **SSOT prix serveur**, **queue number atomique**, **audit trail complet** : tous en place.
6. **Offline kiosk** : IndexedDB + sync = pas de commande perdue si réseau tombe.

### Ce qui manque pour un "V1 RIEL PRODUCTION" 🎯

1. **P0-1 Wizard borne unifié** (V4.1) — demande user explicite #1.
2. **P0-2 Prod lockdown** (queue/cache/debug/healthallowlist).
3. **P0-3 Password kiosk rotaté**.
4. **P1-1 Notifications async** pour libérer HTTP.
5. **P1-2 Observability stack** (Sentry + Grafana).
6. **P1-3 Durcissement endpoints** (`kiosk-event` ability check).

### Délai estimé jusqu'au V1.0.0 taggé prod

- V4.1 wizard : **2-3 sessions** dédiées
- P0-2/3/4 durcissement prod + gates : **1 session**
- P1 quick wins (kiosk-event ability, Sentry) : **1 session**

**Total : 4-5 sessions ciblées** avant tag `v1.0.0`.

Le reste (P2-P3) constitue le post-V1 naturel et peut s'étaler sur 3-6 mois sans bloquer le lancement.
