### A-001 — `loyalty_code` entropy is far below the marketed ~36⁸
**Severity**: P0 | **Category**: security
**Description**: `loyalty_code` is generated by `strtoupper(substr(md5(uniqid()), 0, 8))` in two places (`LoyaltyController.php:82` for `check()` fallback, `LoyaltyController.php:162` for `register()`). `uniqid()` is a timestamp-microseconds string + optional entropy (PHP doc: more_entropy=false → 13 hex chars derived from current time). `md5(uniqid())` truncated to 8 hex chars and uppercased ⇒ alphabet is **0-9 + A-F only** (hex), not full alphanumeric 36 chars. Effective keyspace = **16⁸ = 4.29 × 10⁹**, not 36⁸ = 2.8 × 10¹². That's a **650× collapse** vs the implicit assumption in `mobile/data/loyalty.js:1-9` ("8-char alphanum"). Plus `uniqid()` correlates strongly to clock-time → a guess windowed to last 24 h drops effective entropy by another ~3-4 orders of magnitude.
**Evidence**: `app/Http/Controllers/Frontend/LoyaltyController.php:82`, `:162`; `database/migrations/2026_03_08_145926_add_loyalty_fields_to_users_table.php:16` (VARCHAR(15) UNIQUE — so longer codes are physically allowed).
**Proposed fix path**: replace with `Str::random(10)` constrained to base32 alphabet, or use a checksummed Luhn-style 10-digit code. Document collision-rate budget.
**Counter-argument the implementer will make**: "10 throttled requests/min on `/loyalty/check` (`routes/api.php:1204`) makes brute-force impractical."
**Rebuttal**: enumeration via `/loyalty/scan` (Phase 8.3) and `/loyalty/register` (`throttle:5,1`) is throttled per IP, not per-target. Distributed scan from 1000 IPs = 50K probes/min. Against a hex⁸ keyspace, a 1% population is hit in ~14 hours. AND: anyone with read access to a printed plastic card can recover the code. The entropy claim has to hold pre-rate-limit.

### A-002 — V0 localStorage `idempotency_keys` map is structurally non-idempotent
**Severity**: P0 | **Category**: data / money
**Description**: Agents 1+3 will propose a localStorage `idempotency_keys` set/map on the mobile client to dedupe redeem POSTs. This is broken in 4 enumerable ways:
1. **App reinstall** → localStorage cleared → user can re-submit a previously-acked redeem; backend has no idempotency middleware on `/loyalty/redeem` (`routes/api.php:1212`; middleware list shows only `auth:sanctum`, no `idempotency`).
2. **Device switch** → user logs in on phone B → no shared key history → same logical redeem can replay.
3. **Browser tab duplication** → both tabs read same auth token but different localStorage instances are actually shared on the same origin; however `Storage` API offers no atomic check-and-set, so a TOCTOU lets both tabs send the same key.
4. **Quota exceeded** → `localStorage.setItem` throws `QuotaExceededError` silently in some browsers; the catch path will likely just log and proceed → key never persisted → next refresh retries.
**Evidence**: `routes/api.php:1208-1213` (no `idempotency` middleware on `/loyalty/redeem`); `app/Http/Middleware/IdempotencyKeyMiddleware.php:41` (`enabled` flag is config-gated — check whether `loyalty.redeem` is in `requires_idempotency` list — it is NOT enumerated in any route group seen in `routes/api.php:1212`).
**Proposed fix path**: require server-side `Idempotency-Key` header AND extend `loyalty_transactions` unique constraint to `(user_id, idempotency_key)` for redeem rows where `order_id IS NULL` — current unique is `(user_id, order_id, type)` which collapses to a single row for redeem because `order_id` is NULL.
**Counter-argument**: "The `lockForUpdate` + balance check in `LoyaltyController.php:274,298` prevents over-redemption."
**Rebuttal**: it prevents *insufficient-balance* over-redemption (`points < pointsToRedeem` → 400). It does NOT prevent two redeems each of which is individually valid. Example: user has 200 pts, redeems 100 + 100 in two parallel requests with the same intent. Both succeed; transaction log shows two rows with `order_id=NULL` and the composite unique permits `(user_id=42, order_id=NULL, type='redeem')` exactly once → second insert throws → 500 error returned to user but **points were already decremented** in the first leg of `DB::transaction` because the inserts are inside the same atomic block? — Actually rollback covers it. BUT: the user receives a 500 with no clarity, and if they retry, they double-redeem from a UX standpoint. The "all of the above" failure mode is that backend logs an exception while wallet shows -100 then -100 again. **The unique constraint is doing idempotency work it was never designed for** — `(user_id, NULL, 'redeem')` collapses ALL redeems into one row attempt → migration `2026_03_26_075919:29` is silently a single-redeem-ever lock.

### A-003 — UNIQUE `(user_id, order_id, type)` collapses pre-order redeems
**Severity**: P0 | **Category**: data
**Description**: `database/migrations/2026_03_26_075919_add_unique_to_loyalty_transactions.php:29` declares `unique(['user_id', 'order_id', 'type'])`. In MySQL InnoDB, **NULL is not equal to NULL in UNIQUE constraints** — meaning a user can have unlimited `redeem` rows with `order_id=NULL`. In SQLite (test env, `migration:46-52`), NULL DOES participate in UNIQUE comparisons (a single (user_id, NULL, 'redeem') is allowed; second attempt fails). So tests on SQLite will GREEN and production on MySQL will SILENTLY LET REPLAYS THROUGH.
**Evidence**: `database/migrations/2026_03_26_075919_add_unique_to_loyalty_transactions.php:29`; `app/Http/Controllers/Frontend/LoyaltyController.php:309-318` (insert with `order_id => null`).
**Proposed fix path**: split into two indexes — `unique(user_id, order_id, type) WHERE order_id IS NOT NULL` (functional index) + separate idempotency_key column with its own unique. Or always allocate a stub order_id before redeem.
**Counter-argument**: "We caught this with `KioskLoyaltyDoubleRedeemRefusedTest`."
**Rebuttal**: that test runs on SQLite by default — it asserts the SQLite behavior, not MySQL. Verify by reading `phpunit.xml` `DB_CONNECTION` — typically `sqlite`. The test passes for the wrong reason.

### A-004 — `loyalty_transactions` has NO `branch_id` → cross-branch leak
**Severity**: P0 | **Category**: governance / data
**Description**: `BranchScope` (CLAUDE.md §9) is enumerated as applied to 11 models — `LoyaltyTransaction` is **NOT** in that list (see `database/migrations/2026_03_26_075918_create_loyalty_transactions_table.php:20-33` — no `branch_id` column at all). User earns 500 pts at branch A (Le Cayenne Hénin-Beaumont) then redeems at branch B (future second franchise). Backend `LoyaltyController::redeem` (line 273) does NOT filter by branch — it locks the User row globally. Customer's points are a global wallet, but the operator at branch B has just given a 5€ discount whose earn was on branch A's books. **In a SaaS multi-tenant world this is settlement leakage**; in a single-branch V1 it's invisible but encoded into the schema as an unfixable shortcut.
**Evidence**: `database/migrations/2026_03_26_075918_create_loyalty_transactions_table.php:20-33` (no branch_id); `app/Http/Controllers/Frontend/LoyaltyController.php:273-323` (no branch filter); CLAUDE.md §9 "BranchScope global appliqué sur 11 models" — Loyalty* absent.
**Proposed fix path**: add `branch_id` nullable column + migration backfill from `orders.branch_id` where order_id is set + admin reconciliation report per branch. V1 may accept single-branch posture but the schema must be ready.
**Counter-argument**: "loyalty is a brand-level program, not branch-scoped."
**Rebuttal**: that's a product decision, not a schema decision. The schema must record WHERE earn/redeem happened for accounting reasons (the bistro on Avenue X owes the bistro on Place Y when a customer moves points). This is precisely the franchise scenario `MOBILE_APP_ULTRAPLAN_2026-05-09.md` envisions.

### A-005 — Rate drift cascade if `loyalty_points_per_euro` changes
**Severity**: P1 | **Category**: data / UX
**Description**: Agent-1 will propose normalizing mobile config to `earn_ratio: 10` (= 10 pts / €) to match backend default at `LoyaltyController.php:413`. But the backend permits owner to change `loyalty_points_per_euro` via admin settings (`app/Http/Requests/LoyaltySetupRequest.php:17` allows `min:0, max:1000`). When the rate changes from 10 → 20 mid-cycle:
- Historical `loyalty_transactions` rows show e.g. `+50 pts on 5€ order` (rate=10). The "reason" shown to user is *"Box Nashville"* — no rate captured. User cannot reconcile.
- `pointsToDiscount()` (LoyaltyController:721) divides current balance by current rate. If user accrued 1000 pts at rate=100, their display value is 10€. Owner changes to rate=200 → display becomes 5€. **Stealth half-off**.
- Mobile `redeem_ratio: 100` (loyalty.js:17) is hardcoded; backend `loyalty_points_for_1_euro_discount` default 100 (LoyaltyController:414) is configurable. Drift here changes the discount amount silently.
**Evidence**: `mobile/data/loyalty.js:15-18`; `app/Http/Controllers/Frontend/LoyaltyController.php:289-296,413-414,721-725`.
**Proposed fix path**: store `rate_at_event` and `redeem_rate_at_event` on each `loyalty_transactions` row; expose via `/config` endpoint a versioned bundle; cache for 60s in mobile.
**Counter-argument**: "We never change the rate."
**Rebuttal**: it is admin-editable, validated, and persisted via `Settings::group('loyalty_setup')`. "Never change" is a policy assertion, not a schema guarantee.

### A-008 — Mobile-side `composition_snapshot` ≠ source of truth → loyalty earn on phantom totals
**Severity**: P0 | **Category**: data / money / NF525
**Description**: Listener computes points from `$order->total` (kiosk) or `$order->order_amount` (POS) (lines 96-101). Mobile creates orders via a future endpoint (CONNECTION_PLAN.md:280-298) that has NOT been built yet. ### A-011 — `btoa(fakeHmac)` mock teaches developers the wrong shape
**Severity**: P1 | **Category**: security / governance
**Description**: `mobile/data/loyalty.js:55-58` uses `btoa(\`${userId}:${ts}\`).replace(/=/g,'').slice(0,16)` and labels the variable `fakeHmac`. Anyone reading this file thinks the prod path is "base64-of-string-truncated". Real HMAC requires a server-held secret. When Phase 6 backend tries to validate this on the server-side, devs may mistakenly implement an HMAC verifier that decodes base64 rather than computing `hmac_sha256(secret, payload)`. Also: backend `/loyalty/scan` (`LoyaltyController.php:609-635`) does NOT validate HMAC at all — it parses `FK:<code>` and `<code>` raw. So if mobile sends `LECAY-LOYALTY-12345-{garbage}`, backend regex (`preg_match('/^\+?\d{6,15}$/'`, line 623) on phone fallback won't match, the strtoupper lookup won't match — call returns `customer_not_found`. **The QR mock format will literally fail backend lookup.**
**Evidence**: `mobile/data/loyalty.js:54-58`; `app/Http/Controllers/Frontend/LoyaltyController.php:609-635`.
**Proposed fix path**: drop `btoa` mock entirely. Generate `FK:<loyalty_code>` only on mobile until backend signs HMAC server-side via a new endpoint. Update the V0 mock to match the format backend accepts.
**Counter-argument**: "It's a mock. Devs know."
**Rebuttal**: code reviews 6 months from now will not. The shape itself drifts the integration. Worse: kiosk QR scanner will reject `LECAY-LOYALTY-*` strings because line 611 only strips `FK:` prefix — every other format falls through to phone regex which fails.

### A-012 — QR format choice: D-A (`FK:<code>`) vs D-B (`LECAY-LOYALTY-*`) — D-B is dead-on-arrival
**Severity**: P0 | **Category**: integration
**Description**: Whichever Agent-2 picks, here are the failure modes:
- **D-A picked** (`FK:<loyalty_code>`): collides with anything that prefixes "FK" — e.g. a competitor's QR menu link `FK://menu/...`. Backend strips first 3 chars (`substr($raw, 3)`) — if QR is `FK://menu/123` becomes `//menu/123` → not found → falls through to phone regex → matches if `123` is the only digit run? No, phone regex is full-string `^\+?\d{6,15}$` (line 623) — `//menu/123` fails. Safe but ugly.
- **D-B picked** (`LECAY-LOYALTY-{user_id}-{hmac}`): backend rejects it. `strtoupper($code)` of `LECAY-LOYALTY-12345-abc123` doesn't match any `users.loyalty_code` (which is 8 hex). The phone-fallback regex `\+?\d{6,15}` doesn't match either. Returns `customer_not_found` 200. **Mobile QR cannot be scanned at the kiosk.** Period.
**Evidence**: `app/Http/Controllers/Frontend/LoyaltyController.php:609-635`.
**Proposed fix path**: D-A is the only viable V0 choice. Document in mobile that V0 QR shape is `FK:<loyalty_code>` ONLY. Defer HMAC entirely until backend implements `/loyalty/qr` (which doesn't exist — CONNECTION_PLAN.md:297 says it does, it doesn't).
**Counter-argument**: "We'll add D-B parser to backend."
**Rebuttal**: that's an unspecced change to `LoyaltyController.php` — a backend mutation. The brief is "V0 standalone with stubs", not "modify backend". Scope creep.

### A-015 — `kiosk:order` token replayed against mobile endpoints
**Severity**: P0 | **Category**: security
**Description**: Sanctum `tokenCan('ability_name')` (e.g. `LoyaltyController.php:579`) checks string equality only. A `kiosk:order` token has ability `kiosk:order`; if mobile uses `mobile:order` and the controller checks `tokenCan('mobile:order')`, a kiosk token fails — good. **Counter-argument**: "We'll just give mobile both abilities."
**Rebuttal**: that gives a stolen mobile token full kiosk privileges (e.g. cart creation, pricing override, promo validation as a customer-facing pre-auth call). Token theft is realistic on mobile (SIM-swap, malware).

### A-016 — Apple Wallet pass.json is static → balance stale forever

### A-017 — Google Wallet JWT signed with rotating service-account key
**Severity**: P1 | **Category**: governance
**Description**: Google Wallet "save" URLs are JWT-signed with a Google service-account key (`*.json` secret). If the key is rotated (security best practice quarterly), all previously-issued save URLs break, but already-saved passes on user devices remain — the SIGNED data stays valid until the pass expires. Rotation story is non-trivial: a customer who saved their loyalty pass 6 months ago at key v1, now we're on key v3, can their pass be updated? Only if we re-sign and reissue, requiring user action (open new save URL) OR backend push to the existing pass.
**Evidence**: Google Wallet Loyalty class JWT spec (external).
**Proposed fix path**: document key rotation schedule + backend admin endpoint to bulk reissue passes. V0 can defer wallet entirely.
**Counter-argument**: "We won't rotate the key."
**Rebuttal**: that's exactly what gets you breached. Plan for rotation.

### A-018 — History pagination explodes on long-time customer
**Severity**: P1 | **Category**: UX / perf
**Description**: `LoyaltyController::history()` (line 482) uses `paginate($perPage)` with default `per_page=20`. A long-time customer with 5 years of weekly orders has ~260 earn rows + ~50 redeems → 310 rows, ~16 pages. Fine. But: in mobile V0 mock, `HISTORY` array (loyalty.js:43-51) has 7 hardcoded entries. When the mobile mock pretends to paginate but is really sliced, deep pagination tests against the backend will reveal that `paginate()` on `loyalty_transactions` has NO ordering covering index — the query orders by `created_at DESC` but `created_at` is not indexed (`migration 075918:34` only has `timestamps()`). On a table with 1M+ rows (multi-tenant SaaS scale), filesort kicks in. Slow.
**Evidence**: `app/Http/Controllers/Frontend/LoyaltyController.php:482-483` (orderByDesc created_at); `database/migrations/2026_03_26_075918_create_loyalty_transactions_table.php:23-34` (no composite (user_id, created_at) index).
**Proposed fix path**: add covering index `(user_id, created_at DESC)`. Cap pagination depth at 100 pages or implement cursor pagination for mobile.
**Counter-argument**: "We're small, this is premature optimization."
**Rebuttal**: index is cheap; filesort scans are expensive. The index pays off in week 1 of multi-tenant rollout (BRAIN.md §1 mentions SaaS B2B vision).

### §3.bis — Additional contestation surfaced during deliverable check

### A-019 — `loyalty_transactions` is NOT in the NF525 audit chain
**Severity**: P0 | **Category**: governance / fiscal
**Description**: BRAIN.md §8 lists `audit_logs` and `z_reports` as HMAC chain-signed. `loyalty_transactions` is **not** in that chain. A malicious admin (or compromised DB credential) can DELETE or UPDATE a redeem row directly and there's no detection. NF525 requires immutability of transactional records related to fiscal value — and a 100€-of-loyalty redemption is fiscally equivalent to a 100€ discount on the receipt. Auditors will ask.
**Evidence**: `app/Services/Fiscal/AuditLogService.php` (no loyalty_transactions writes); CLAUDE.md §8 ("audit chain": only `audit_logs` + `z_reports`).
**Proposed fix path**: every `loyalty_transactions` insert/update logs to `audit_logs` via AuditLogService::write() with the row's hash. V1 deliverable.
**Counter-argument**: "Loyalty isn't fiscal."
**Rebuttal**: it materially reduces VAT-bearing revenue at the moment of redeem. NF525 doesn't care about the field name — it cares about discount events. Bercy auditor wins.

## §4 — Worst-case scenario walks

### W-001: Money loss via concurrent redeem from two devices
1. User has 500 pts. Opens mobile on Phone A (Safari) and Phone B (Chrome). Both authenticated.
2. Phone A: tap "Redeem 500 pts → 5€ off cart".
3. Phone B simultaneously: tap same.
4. Two `POST /loyalty/redeem {points: 500}` arrive at backend within 50ms.
5. `lockForUpdate` serializes them (`LoyaltyController.php:274`). Tx1: decrements to 0, inserts redeem row `(user_id=42, order_id=NULL, type='redeem')`. Tx2: re-reads, finds points=0, returns "Points insuffisants" (line 298).
6. Tx1 returns success. But: there is NO `order_id` linkage. User now applies the 5€ discount in TWO separate carts on the two devices. Server has no idea both carts are claiming the same 500 pts. Both orders get placed with `discount=5.00`. Cashier honors both. **5€ loss.**
**Mitigation**: pre-order redeem MUST allocate a stub order or pending_redemption row. Today's flow allows the redeem-then-spend-twice gap.
**Evidence**: `app/Http/Controllers/Frontend/LoyaltyController.php:312` (`order_id => null` on redeem insert).

### W-002: Cross-branch leak when SaaS rollout adds branch B
1. Single-branch V1 ships. Customer 42 earns 1000 pts at branch A.
2. Year 2: branch B opens. Same customer visits, scans QR.
3. POS at branch B reads `loyalty_code` → backend resolves user 42 → returns balance 1000.
4. Operator B applies 10€ discount. `redeem` row inserted with `loyalty_code='ABC12345', order_id={branch_B_order_id}, source_surface='pos'`.
5. Branch A's accounting shows: customer 42 contributed 1000 pts of liability. Branch B's accounting shows: 10€ discount given.
6. **Settlement question**: branch A "owes" branch B 10€ in loyalty redemption value. No table records this transfer. SaaS revenue-sharing is unrecoverable post-hoc.
**Mitigation**: A-004 fix — add branch_id to loyalty_transactions.
**Evidence**: `database/migrations/2026_03_26_075918_create_loyalty_transactions_table.php` (no branch column).

### W-003: GDPR data deletion orphans `loyalty_customer_code` on orders
1. Customer 42 requests account deletion (RGPD article 17).
2. `users.id=42` DELETE → CASCADE on `loyalty_transactions.user_id` (migration:32 FK CASCADE) → all loyalty rows deleted.
3. BUT: `orders.loyalty_customer_code` is just a VARCHAR — no FK. The code `ABC12345` stays on historic orders.
4. Later, customer 99 registers and `register()` (LoyaltyController:162) generates `ABC12345` (collision against deleted user's code). Why is this possible? Because user 42's row is gone → UNIQUE on `users.loyalty_code` no longer reserves `ABC12345`.
5. New user 99 now "owns" historic orders attributed to old user 42's code → privacy breach + accounting fiction.
**Mitigation**: tombstone deleted users (soft delete + retain loyalty_code) OR strip `loyalty_customer_code` from orders on user-delete.
**Evidence**: `database/migrations/2026_03_08_145926_add_loyalty_fields_to_users_table.php:16` (UNIQUE column drops constraint when row deleted); no migration nulls `orders.loyalty_customer_code` on user delete.

## §6 — Concession list (where I might be wrong)

I would update my position if shown:

- **A-001 entropy claim**: my hex⁸ vs alphanum⁸ math assumes `md5(uniqid())` truncated and uppercased yields only 0-9A-F. If there is a regeneration loop elsewhere that retries until alphanum (I did not find one in `LoyaltyController.php`), the keyspace is wider. **Evidence I need**: any other code path that mutates `loyalty_code` post-md5.

- **A-003 NULL-in-UNIQUE behavior**: I claim MySQL InnoDB allows multiple NULL values in UNIQUE indexes. This is widely documented but I have not seen the actual UNIQUE constraint exercised under MySQL load here. **Evidence I need**: a production-grade integration test on MySQL (not SQLite) demonstrating two `(user_id, NULL, 'redeem')` rows both succeed.

- **A-006 LoyaltyReward absent**: I grep'd the models directory and found only Consent + Transaction. If a reward catalog lives in a different namespace (e.g. inside Smartisan\Settings as a JSON blob), the picture is different. **Evidence I need**: any `loyalty_rewards` table reference in migrations or settings groups.

- **A-008 PricingService re-resolve**: my position is that `$order->total` can drift post-creation. If the codebase guarantees `total` is write-once at create and never mutated, my P0 downgrades to P2. **Evidence I need**: audit of all `Order::save()` calls that mutate `total` post-creation.

- **A-009 partial refund asymmetry**: if the product policy says "loyalty earn is NOT prorated on partial refunds, by design", then this is correct behavior not a bug. **Evidence I need**: explicit business rule in `docs/BUSINESS_RULES.md` or an owner statement.

- **A-015 ability replay**: if mobile token never gets `kiosk:order`, the replay vector is moot. **Evidence I need**: the eventual `KioskMachineLoginController`-equivalent for mobile actually scoping abilities to `mobile:order` only — and a grep proving no controller checks `tokenCan('kiosk:order') || tokenCan('mobile:order')`.

- **A-018 history index**: at V1 single-branch scale this is academic. The cost is one index in a migration, but the regression risk is also low. I could be over-indexing for scale that won't arrive.

- **W-002 cross-branch**: this is a future-leak, not a present bug. If the product owner asserts "we will never enable multi-branch loyalty without dedicated migration", this contestation downgrades to a tracking item, not a P0.
