## 3. RED-team disputes

1. **PREPARED→DELIVERED short-circuit / skip pickup wall view?** —
   No short-circuit. DELIVERED removes the row from OSS wall (allowlist
   `whereIn(status, [PREPARING, PREPARED])`). Order is gone on the next
   poll OR immediate OrderStatusChanged broadcast (after-commit) — visual
   pickup window is bounded by min(WS latency, 2s disconnect poll, 60s
   connect poll). Not a defect — intended UX (cashier removes served
   ticket from queue). DISPUTE REJECTED.

2. **IDOR — another branch's order?** —
   `Order::class` has `BranchScope` global (Order.php:92), so route-model
   binding `{order}` returns 404 on foreign branch_id for non-Admin. Defense
   in depth: OrderService.php:1872-1879 calls `abort(403)` for non-Admin staff
   mismatched branch. Two layers. DISPUTE REJECTED.

3. **Wave Y rate-limit bypassable?** —
   Limiter `pos-order-update` (RouteServiceProvider.php:158-161,
   config `pos.rate_limit.order_update` default 120/min) keyed by
   `$request->user()->id ?: $request->ip()` — same key as Wave Y
   admin-mutation pattern. Idempotency middleware also caches 2xx replay
   (same minute bucket key per L2980-2987 Vuex action). Not bypassable
   short of session-stealing (out of scope). DISPUTE REJECTED.

4. **OSS removal latency drift under load?** —
   Brief said "6.1s baseline" — actual is bounded by Echo WS broadcast
   (sub-second when connected) + 60s connected-poll fallback. If WS
   drops, fallback drops to 2s (OssSyncService.js:16). Under burst load
   the only contention point is `OssSyncService._abortController` (single
   in-flight enforced L41) — already correctly serialized. No latency
   regression vector identified. DISPUTE REJECTED.

5. **WakeLock TV — network flap, screen sleeps + reactivates?** —
   `visibilitychange` handler re-acquires (PreparingAndReadyComponent.vue:147-150).
   But `online`/`offline` events NOT bound — a Wi-Fi drop that keeps the
   tab visible would NOT re-trigger acquire, though the sentinel survives
   the network flap (WS reconnects separately). Browser auto-releases the
   sentinel only on tab switch / OS lock, not on net loss. **Not a defect**,
   minor V1.0.2 hardening opportunity. DISPUTE PARTIALLY UPHELD as F-INFO.

## 4. Cloud-deploy risks

1. WS broadcast under managed Pusher/Soketi: dispatch is after-commit
   (OrderService.php:1994-1999, wrapped try/catch — Log::warning only).
   If broadcast queue worker dies in cloud, OSS wall falls back to 2-60s
   polling — SYNC-2 budget intact. NF525 chain unaffected (audit_logs
   write inside transaction).
2. `oss-public` throttle is IP-keyed — behind cloud LB / NAT, the LB IP
   becomes shared. 60/min ceiling could throttle a fleet of 5+ walls
   sharing a NAT. Brief mentions this is documented in RouteServiceProvider.php:205-214.
   Not a blocker pre-cloud but watch metric after deploy.
3. Idempotency middleware uses cache layer — Redis required in cloud
   (file/database cache would silently degrade replay protection). Out
   of scope this audit; covered W6.

## VERDICT

**GREEN — no V1 ship blocker, no cloud risk requiring action.**

The Wave X2 POS shortcut wire-up reuses the canonical
`posOrder/changeStatus` Vuex action, which routes through
`PosOrderController::changeStatus` → `OrderService::changeStatus` →
`OrderStateMachine::allows(PREPARED, DELIVERED)` (legal transition),
then dispatches `OrderStatusChanged` after-commit which trips the OSS
public allowlist (`whereIn(KIOSK, TAKEAWAY)` × `whereIn(PREPARING,
PREPARED)`) to drop the order from the customer wall. Two-layer
branch isolation (BranchScope + abort(403) staff guard). Idempotency
middleware + `throttle:pos-order-update` (120/min user-keyed) both
applied. 5 RED disputes filed: 4 rejected, 1 partially upheld
(WakeLock missing `online`/`offline` re-acquire — V1.0.2 backlog,
non-blocking).

Brief inaccuracies surfaced: (a) no `PosShortcutOrderController` class
exists; (b) "6.1s OSS removal latency baseline" not verified —
actual bounds are sub-second WS / 2s disconnected / 60s connected.
