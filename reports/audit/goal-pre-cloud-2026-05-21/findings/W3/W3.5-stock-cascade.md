## 2. Findings

- **P0**: 0
- **P1**: 0
- **P2**: 1 — `StockLevel::lockForUpdate()` (StockService.php:90, 394) has no explicit lock_wait timeout. Relies on MySQL default `innodb_lock_wait_timeout=50s`. Under cloud RDS hot-SKU contention, slow worker can pile decrements at 50s each.
- **P3**: 1 — `StockDecrementFailedEvent` intentionally **unwired** (event docstring lines 17–18). No ops alert subscriber. Log::error is the only signal until ops team adds listener.

## 3. Cloud risks

- **Redis Cluster + SETNX**: `Cache::add` is a single-key SETNX (no cross-slot Lua). Safe atomic per hash slot. Edge case: primary fails mid-write under async replication → guard lost on new primary → re-fire double-counts ONE order's `daily_consumed_qty`. Blast radius bounded (documented inline lines 305–310). NOT a fiscal counter — `stock_movements` SHA1 idempotency remains the SSOT.
- **Distributed lock on 86 cron**: `withoutOverlapping()` + `onOneServer()` already provides cache-backed scheduler lock. Cartography risk MITIGATED.
- **lockForUpdate indefinite**: confirmed P2 above. Recommend explicit `SET innodb_lock_wait_timeout=10` per StockService transaction in cloud profile.
- **RDS replica lag**: config/database.php has NO `sticky => true` setting and no read/write split today (single connection). When cloud profile adds read replicas, KioskMenuService DB miss after `Cache::forget` could read stale `is_available=true` for replica-lag duration (~30s worst). FUTURE risk — add to cloud profile checklist; not currently exploitable.
- **Trigger preservation on RDS**: migrations use `DB::unprepared("CREATE TRIGGER...")` — RDS MySQL fully supports. `TRUNCATE` bypass already documented in migration lines 53–56; mitigation = Ansible `REVOKE TRUNCATE` task (deploy-doc scope).
