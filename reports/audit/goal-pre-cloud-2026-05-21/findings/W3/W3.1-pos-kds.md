## 5. RED-team disputes (Adversarial supervisor)

### R-D1 — Echo silent-failure widens latency window (P2/P3 cloud-only)
At `KitchenDisplaySystemComponent.vue:1877-1879`, an Echo subscription failure logs `console.warn('[KDS] Echo subscription failed:', e.message)` and falls back to polling. There is no UI status banner for the per-tab failure (the `kds-sync-mode-banner` covers cadence mode, not auth failure on subscribe). On cloud cutover with Pusher cluster failover or expiring Sanctum subtokens, KDS chefs can stay on polling (5-60s) without realising it. **Disputes "always sub-second" P0/P1 invariant**; production-acceptable since the chain falls back to polling, but a manual observability gap.

### R-D2 — `OrderCreated` payload omits item-level allergens (potential cloud surprise)
`PersistOrderCreatedToOutbox.php:32-43` ships only `order_id, queue_number, _origin, payment_method, payment_status, payment_pending_counter, status, order_type, total, created_at`. The KDS client receives the `OrderCreated` envelope then **re-fetches** items via HTTP (`_debouncedRefresh()` line 1860). Under RDS replica lag (≥write-after-read window), the replica may not yet have the `order_items.allergens_snapshot` row when KDS fetches. **Cloud risk**: stale empty allergens on first paint, recover on the next debounced refresh. Severity P2.

### R-D3 — Idempotency replay can return stale 2xx after server-side state advance (P2 cloud-only)
The middleware caches the 2xx response body (line 145-151). If POS retries POST identical payload + same `X-Idempotency-Key` after the KDS chef has bumped the order from `ACCEPTED → PREPARING`, the replay returns the original 2xx (creation-time) snapshot, masking the live state. The frontend overlays Vuex state from Echo events, so the practical impact is small, but a thin window exists where POS reads "fresh creation snapshot" while KDS shows "preparing".

### R-D4 — Wave Q-4 "allergens empty across the board" — RESIDUAL VIGILANCE
Anchor 01-pos.md:263 documents "Allergens snapshot verified post-seeder NOOP (fake allergens cleared)". The allergen-rendering JS in KDS still runs even when arrays are empty (the badge component renders nothing on `[]`). No XSS/rendering risk. But the **invariant "allergens display whenever populated"** depends on item-level allergens actually being populated at seed/CMS time. Drift risk if CMS adds an item without allergens metadata.

### R-D5 — Network-flap duplicate event from listener replay vs job replay
Two independent dedup layers exist:
- Listener-level `firstOrCreate` (PersistOrderCreatedToOutbox line 25, sha1 key).
- Job-level `lockForUpdate + dispatched_at` claim (DispatchDomainEventsJob line 65-86).

RED challenge: What if the queue worker dies BETWEEN listener `firstOrCreate` row insert AND `DB::afterCommit → dispatch`? Answer: cron `outbox:retry-failed` (referenced line 77) retries on `dispatched_at IS NULL`. **No duplicate**, but a potential latency stretch (cron cadence-dependent) on worker crash. P2 cloud.

### R-D6 — Admin polling 60s and branch staff sub-second create a sync-mode asymmetry
Admin viewing the KDS as cross-branch supervisor sees orders up to 60s after the chef. If owner uses the central-admin KDS as the **canonical reconcile screen** during a service rush, decisions can lag actual kitchen state. This is documented (B.3 comment) but acceptance-gated to owner workflow.
