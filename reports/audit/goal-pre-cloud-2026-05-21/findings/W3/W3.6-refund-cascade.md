## 4. RED-team challenges — resolution

| # | Challenge | Verdict |
|---|---|---|
| Q1 | 2 distinct `X-Idempotency-Key` → 2 mirrors before UNIQUE fires? | **MITIGATED**. DB UNIQUE is synchronous & atomic. Second `INSERT` raises SQLSTATE 23000 — `PosOrderController:90-95` returns 409 `MIRROR_ALREADY_EXISTS`. Test `RefundCounterEntryUniqueParentTest::http_second_call_returns_409` confirms. **Residual:** two concurrent transactions can BOTH allocate `fiscal_sequence_no` via `FiscalSequenceService::next()` before either INSERT — the loser's allocated sequence becomes a **gap candidate** (fiscal_alloc_error_at retry handles per CLAUDE.md §8). Not a money-leak; sequence wastage only. |
| Q2 | What defines "sealed"? Cross-Z-day handled? | `SealedOrderGuard:46-52` — `ZReport.opened_at < order.created_at` AND `closed_at >= order.created_at` AND `fiscal_sequence_no IS NOT NULL`. Single Z record-window match. Cross-Z = post-Z (sealed) — mirror path required. **No gap.** |
| Q3 | User already received bonus via `manual_add` AFTER original earn? | `LoyaltyService:71-74` filter is `where order_id = $order->id AND type='manual_add'` scoped to THIS order. `LoyaltyController::manual_add` writes with `order_id=NULL` (lines 226, 315 verified) — no scope collision. Bonus `manual_add` on unrelated orders does not block refund. **Clear.** |
| Q4 | RDS slow replication >5s — dual-create race? | UNIQUE is enforced on the **primary** (writer). Reads from replica are irrelevant to the INSERT path. Race window = wall-clock between `SealedOrderGuard` SELECT and `Order::create` INSERT — bounded by single DB::transaction on primary. **MITIGATED.** |
| Q5 | cashBack audit_logs append fails → rollback → customer cash state? | `PaymentService:128-188` wraps Transaction+balance+AuditLogService inside DB::transaction. If AuditLogService HMAC chain insert fails (e.g. chain-head missing), the **Transaction row + balance increment are also rolled back** — no orphan cash credit, no orphan balance bump. `RefundCreated::dispatch` uses `DispatchableAfterCommit` → never fires on rollback. **Customer money state correct (no false credit).** Customer never sees a refund that wasn't fiscally recorded. |

## 6. Cloud risks (managed RDS / multi-AZ)

1. **`recordCashBackMovement` best-effort log** (`PaymentService:175-176`) — self-shielded `try/catch + Log::warning`. On cloud, log shipping latency could mask drawer drift. Acceptable per existing F-003 design (CLAUDE.md §8).
2. **`Log::channel('fiscal')`** (`RefundWithCounterEntryService:225`) wrapped in try/catch (line 232). Acceptable; logs are best-effort, the DB row + audit chain are the source of truth.
3. **DispatchableAfterCommit + DB primary** — listeners only fire after primary commit. Read replicas may lag but cannot cause double-fire.
4. **Two-DB write split** (read-replica reads for `SealedOrderGuard` SELECT, primary write for `Order::create`) — Eloquent's `lockForUpdate` paths force primary. `SealedOrderGuard` does NOT use lockForUpdate but UNIQUE constraint is the final arbiter.
