## §8 Cloud risks (V1.0.X multi-instance / multi-site cutover)

- **P2 — Key rotation orchestration** : `LOYALTY_QR_SECRET` is process-local env var. On multi-instance cloud (e.g. 2 web pods) a rolling deploy with new secret causes ~30s window where pod-A signs with key-new but pod-B verifies with key-old → `qr_invalid_signature` 200 response (graceful per invariant §12). Mitigation : (a) atomic env update via secrets manager, (b) accept short window of false-negatives, (c) clients auto-retry on `error_code=qr_invalid_signature` by minting fresh token.
- **P2 — Nonce table growth** : `loyalty_qr_nonces_consumed` has no automated retention cron in V1. Migration comment line 24-27 mentions "6-month rolling retention" but no cron job exists. At scale (17 sites × N customers × per-5-min mint), table could grow rapidly. V1.0.X TODO : add scheduled `DELETE WHERE consumed_at < NOW() - INTERVAL 6 MONTH`.
- **P3 — Ledger idempotency on multi-instance** : UNIQUE(user_id, order_id, type) is DB-level → safe across pods. Verified. No additional risk on cloud cutover.
- **P3 — Legacy plaintext retirement** : `LOYALTY_QR_ACCEPT_LEGACY_PLAINTEXT` default `true`. Production cloud cutover should keep `true` for transition window, then flip to `false` once `loyalty.qr.legacy_plaintext` log channel shows zero volume.
