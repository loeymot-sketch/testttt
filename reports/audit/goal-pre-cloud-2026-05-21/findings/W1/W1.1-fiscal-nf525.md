### P1 (must-address-before-cloud-cutover)
**[P1-W1.1-01]** `database/migrations/2026_04_22_000002_create_audit_logs_table.php:138-140` and `2026_05_09_160000:30-32` and `2026_05_10_010000:46-50` — **TRUNCATE bypasses MySQL triggers**. Mitigation documented in each migration header as "revoke TRUNCATE permission on production DB user (deploy doc, not migration scope)". Memory `START HERE` claims this is "mitigated via Ansible task CVP0-1, commit `f840c3ef5`", but the mitigation lives in an **infra repo**, not in this repo's migrations. On a cloud cutover (RDS), the equivalent `REVOKE TRUNCATE` / `REVOKE DROP` policy must be re-applied on the managed DB user.
  - reproduction: `mysql -uprod -p -e "TRUNCATE audit_logs"` on a freshly-provisioned RDS user with default GRANTs would succeed, silently wiping the chain.
  - evidence: trigger SQL inside migrations cannot intercept `TRUNCATE` (well-known MySQL semantic: triggers fire on per-row DELETE; TRUNCATE is DDL).
  - recommendation: gate the cloud cutover behind a verifiable IAM/SQL policy that revokes `DROP, ALTER, TRUNCATE, RENAME, REFERENCES` on `audit_logs, z_reports, cash_movements, cash_drawer_sessions, order_payments` from the application-runtime DB user. Add a smoke test that `TRUNCATE audit_logs` returns ERROR 1142 against the prod user.

## RED-team dispute

**Q1 — Is the chain ACTUALLY append-only? Find any code path that could UPDATE or DELETE `audit_logs` rows.**

Grep across `app/` and `database/` for any UPDATE/DELETE path on `audit_logs` / `AuditLog::` returned EMPTY (commands `grep -rn -E "audit_logs.*->(update|delete)|AuditLog::.*->(update|delete)|DB::table\('audit_logs'\)"` and `AuditLog::.*update|->update.*current_hash|->update.*prev_hash`). The only writer is `AuditLogService::performInsert()` line 134-192, which performs `AuditLog::create([...])` and catches `QueryException` only for retry on UNIQUE violation. **No mutation path exists in code.** DB triggers (MySQL + SQLite) catch any external attempt. **VERIFIED append-only at both layers.**

**Q2 — Triggers preserved on managed RDS migration?**

Not preserved automatically. Managed RDS / Aurora restore from `mysqldump` will recreate triggers **only if `--triggers --routines --events` flags are passed**. Recommend cloud-cutover runbook mandate: post-restore `SHOW TRIGGERS LIKE 'audit_logs%'` returns 2 rows; `SHOW TRIGGERS LIKE 'z_reports%'` returns 1; `SHOW TRIGGERS LIKE 'cash_movements%'` returns 1; etc. Also: `php artisan migrate:status` may show all migrations applied while triggers are silently absent if `mysqldump` was raw `--no-triggers`. The integrity check this repo ships (`fiscal:verify-chain --all`) re-walks data but does **not** assert trigger presence. **GAP — recommend adding `Tests/Feature/Sentinels/FiscalTriggersPresenceSentinelTest` that introspects `information_schema.triggers` on MySQL.** Logged as P1-W1.1-04 below.

**Q3 — Any time-of-check/time-of-use race in `allocateSequence`?**

Re-read `FiscalSequenceService::next()` lines 57-114 carefully. The sequence is:
1. acquire `Cache::lock('fiscal_seq_b{n}', 5s)` — up to 3s wait
2. open DB transaction
3. `SELECT MAX(fiscal_sequence_no) ... FOR UPDATE` on rows scoped by `branch_id`
4. return `$max + 1`
5. release cache lock (idempotent)

**Triple defense per CLAUDE.md §8 confirmed**:
- Cache lock serialises at app layer.
- DB `lockForUpdate()` serialises at storage engine layer (gap-free MAX read).
- Unique constraint `orders_branch_fiscal_seq_unique` rejects any collision at commit.

**Subtle issue**: the service RESERVES the number but does NOT persist it on the Order row. The caller (`PaymentService.php:241-242`, `OrderService.php:1006`, `FrontendOrderService.php:1153-1173`, `RefundWithCounterEntryService.php:125`) is responsible for atomically writing back inside the **same transaction**. Grep confirms 4 callers — and each one assigns `$locked->fiscal_sequence_no = $next->next($branchId)` inside an existing `DB::transaction`/`lockForUpdate` block. However, the service header (lines 24-26) explicitly says *"the caller is responsible for persisting it on the Order row inside the same transaction (wire-in deferred to POS-9.4.2b / BLOCKER OrderService)"*. If a caller ever forgets the same-transaction wrapping, the cache lock would release before the Order row writes — opening a TOCTOU window where two callers both read `MAX=N` and both go to write `N+1`. **The DB UNIQUE rescues this case (second write fails) but the failed allocation would orphan a `fiscal_alloc_error_at` flag.**
  - finding: P3-W1.1-05 — add an `assertSameTransaction()` callable hook the service can verify at runtime, or document the caller contract in a sentinel test (`Tests/Feature/Sentinels/FiscalAllocCallerTxSentinelTest`) that mocks the caller and asserts each call site is inside a transaction.

**Q4 — `composition_snapshot` truly immutable post-creation?**

Comprehensive grep:
- `OrderItem.php:44` — listed in `$fillable` (necessary for `create()`).
- `OrderService.php:475/894/1358` — `'composition_snapshot' => json_encode(...)` inside `OrderItem::create([...])` or `->insert([...])` arrays.
- `PricingService.php:291` — same, inside `create()`.
- `FrontendOrderService.php:442` — same.
- `RefundWithCounterEntryService.php:146` — passes parent's snapshot as-is into the mirror's create payload (`'composition_snapshot' => $item->composition_snapshot`). The mirror is a NEW `order_items` row (refund mirror order), not an update of the parent.
- `StockService.php:280`, `KitchenDisplaySystemOrderService.php:383`, `OrderItemResource.php`, `KDSOrderItemsResource.php`, `OrderDetailsResource.php`, `PosOrderController.php:255/287` — all READ paths.
- `BackfillAllergensSnapshotCommand.php`, `MenuHealLightV2Command.php`, `MenuHealLightV3Command.php` — doc-string only ("composition_snapshot historical preservation: add-only").

**No UPDATE path found.** `ValidatesAddonRoles.php:54-64` documents that even internal callers writing through the FormRequest cannot violate snapshot integrity (validation rules enforce structure pre-create). **VERIFIED immutable.**

## Pre-cloud risks (chain copy strategy / trigger preservation / 6y retention / replica lag)

### Top 3

1. **Trigger preservation across managed-RDS restore** *(P1-W1.1-04 — RED-team Q2)*
   `mysqldump | mysql` workflows must use `--triggers --routines --events` AND post-restore `SHOW TRIGGERS` must confirm 4+ triggers (`audit_logs_no_update`, `audit_logs_no_delete`, `z_reports_no_delete`, `cash_movements_no_delete`, `cash_drawer_sessions_no_delete`, `order_payments_no_delete`). Aurora snapshots preserve triggers; cross-engine migrations (MySQL → Aurora MySQL) preserve; cross-major-version (MySQL 5.7 → 8.0) preserves. **Risk**: a logical dump (e.g. AWS DMS in CDC mode) often omits triggers by default — DMS-based cutover is high-risk for fiscal compliance.
   - **Mitigation**: prefer snapshot-restore (binary) over DMS (logical) for the initial cutover. Add a post-cutover gate: `INSERT INTO audit_logs ... ; UPDATE audit_logs SET payload='tampered' WHERE id = LAST_INSERT_ID();` MUST return ERROR 1644 (signal). If it succeeds, ABORT cutover.

2. **TRUNCATE permission on prod DB user** *(P1-W1.1-01)*
   On a freshly-provisioned RDS, the application-runtime user inherits broad default GRANTs from the master credentials. `REVOKE DROP, ALTER, TRUNCATE, RENAME, REFERENCES ON {tables}` must be in the IaC (Terraform/Ansible) AND verified post-cutover. The repo's `f840c3ef5` Ansible task targets on-prem; **must be ported to cloud-IaC** for the cutover.
   - **Mitigation**: pre-cutover smoke test `TRUNCATE audit_logs` against the runtime user → must return ERROR 1142 (privilege error).

3. **Replica lag → `verifyChain` reading stale tail** *(NEW — emerges from cloud topology)*
   In single-writer / multi-reader RDS topologies, `fiscal:verify-chain` invoked against a replica would re-walk a chain that may lag behind the writer by seconds. A real tamper appearing in the lag window would surface as "CHAIN OK" on the replica then "TAMPER" on the writer minutes later. The cron in `app/Console/Kernel.php` (`fiscal-chain-monitor`) and the on-demand operator command share `Kernel::activeBranchIds()` but BOTH route through `DB::connection()` — the default connection.
   - **Mitigation**: pin the verify command to the primary in the cloud runbook (`config/database.php` `sticky => true` or a dedicated `mysql_writer` connection). Add a `--connection=writer` flag if needed (additive, non-frozen).

### Additional pre-cloud notes

- **6y retention**: enforced at code level (migration `2026_04_22_000002::down()` rejects production rollback). Cloud-cutover must NOT include automated `migrate:rollback` in any disaster-recovery script. **Recommend explicit grep on Ansible/Terraform for `migrate:rollback` references.**
- **Fiscal secret rotation**: `assertProductionSafe()` (AuditLogService.php:303-327, ZReportService.php:702-726) enforces min 32-char secret + rejects dev sentinels. Cloud cutover requires the prod secret to be in Secrets Manager / Parameter Store, NOT in the `.env` file (because env-edit attack surface via `SiteService` — flagged in AppServiceProvider:115-121 header comment, V1.0.2 backlog). **Cloud cutover SHOULD strip APP_DEBUG / FISCAL_AUDIT_SECRET from any env-editor allowlist.**
- **HMAC chain canonical hash stability**: `canonicalise()` sorts JSON keys recursively + uses `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE` (AuditLogService.php:335-352) — stable across PHP 8.x. Verify cloud PHP runtime is ≥ 8.0 (assumed; not validated by this audit).
- **Soft-delete coverage in MAX**: LOCK plan `LOCK_FISCAL_WGS_Z6_P1_2026-05-19.md` confirms `withTrashed()` was added on `FiscalSequenceService:97-98` post-Wave-M to prevent sequence_no re-use if an Order is soft-deleted after allocation. Owner countersign tacit 2026-05-20. NF525 chain verified `CHAIN OK` post-commit. **GREEN.**
