## 4. Findings

### P0 — 1 finding

**P0-#1 — Cache driver atomicity not enforced for `file`/`database` in prod**
The boot guard at `AppServiceProvider:214-220` forbids only `array` and `null`. The middleware's `acquire()` semantics (L98-103) require **atomic SET NX EX**. Laravel's `Cache::add()`/`Cache::lock()` is atomic on Redis/Memcached only; the `file` driver simulates locks via filesystem flock and is **not safe across PHP-FPM workers under cloud ALB load** (race window between `find` L86 and `acquire` L99). Production migration to AWS without a Redis-cluster guard could silently downgrade idempotency atomicity.
**Risk**: dual-instance ALB scenario → two workers each pass the `find()=null` gate, both `acquire()` succeed on file driver → double-charge / double-cash-drawer.
**Mitigation**: extend `$forbiddenCacheDrivers` to include `file`, `database`; require `redis`/`memcached`. OR add an explicit `idempotency.cache_store` boot-guard requiring redis.

### P1 — 2 findings

**P1-#1 — Stripe 300s replay-tolerance vs long delayed-replay attack**
`Stripe.php:222` uses `constructEvent(..., 300)`. Attacker that re-uses a captured signed payload after 300s is rejected at signature layer (good). But within the 300s window, signature passes; idempotency then relies on `webhook_events.UNIQUE(provider, webhook_id)`. Risk only if attacker can replay a captured signed payload **within 300s** AND the original event was never processed (DLQ stuck) — narrow but theoretically exploitable on cold-storage replay. Defense-in-depth would log + alert on `wasRecentlyCreated=false` rate spikes.

**P1-#2 — `IDEMPOTENCY_FAIL_OPEN=true` lets storage outage downgrade to app-layer UNIQUE**
Config L23 default false (safe), but env-flag override is one toggle away. App-layer UNIQUE (`orders.branch_id+idempotency_key`) is the documented defense-in-depth (middleware doc L23-25), but pre-cloud it should be explicitly verified covering all 23 required routes (cash-drawer open/close + change-status × 6 may not have an app-layer UNIQUE — only orders does).

### P2 — 1 finding

**P2-#1 — Senangpay HMAC: no constant-time path before `hash_equals`**
`Senangpay.php:108-110` uses `hash_equals` (timing-safe) — correct. But the canonical-string composition (L107) does not strip/normalize the `msg` field, which Senangpay could contain spaces. Low risk; reproduces what handler signed only.

## 6. Top-3 pre-cloud risks

1. **CACHE_DRIVER guard incomplete** — must extend forbidden list to include `file` and `database` before AWS multi-AZ deploy. Without Redis (or Memcached), middleware atomicity breaks under multi-worker concurrency. (P0-#1)
2. **Secrets vault** — `STRIPE_WEBHOOK_SECRET`, `SENANGPAY_SECRET_KEY`, `LOYALTY_QR_SECRET`, `IDEMPOTENCY_MIDDLEWARE_ENABLED` must transit via AWS SSM/Secrets Manager + KMS, not plaintext `.env`. Currently env-only.
3. **ALB rate-limit / replay throttling** — no application-level rate-limit on `/payment/stripe-webhook/` or `/payment/senangpay-webhook/`. Should add WAF rule + per-IP throttle at ALB to mitigate DLQ-replay floods within the 300s Stripe tolerance window.
