## 5. L'IA écrit-elle en base, ou propose-t-elle ? (le motif à reprendre)

**Elle propose ; un humain valide ; SEULE l'action humaine déclenche l'effet métier.** Preuves :

- **Facture** : `PurchasingScanController::scan()` (`:91-121`) écrit bien des lignes en base immédiatement après la lecture IA — mais avec `status=proposed` sur `PurchaseLine` et `status=draft` sur `PurchaseDocument` (`:99,113`). C'est un brouillon, pas un effet stock. Le stock n'est débité/crédité que dans `apply()` (`:191-255`), qui exige un appel HTTP séparé de l'owner avec les cibles choisies, et qui appelle `PurchaseService::validateDocument()` (`:252`) — jamais l'IA elle-même.
- **Uber** : `UberPhotoCaptureController::scan()` (`:59-133`) crée une `UberTicketCapture` et y stocke la lecture (`extracted`), mais ne crée **aucune commande**. Le commentaire de tête du contrôleur le dit explicitement (`:20-26` : « RIEN n'est encore parti : aucune commande, aucune impression, aucun stock touché »). Seul `confirm()` (`:141-219`), déclenché par une action humaine explicite, appelle `UberOrderIngestor::ingest()` (`:193`) qui crée réellement la commande envoyée en cuisine.
- Dans les deux cas, le prix/la cible ne sont jamais calculés ou décidés par l'IA : les prix lus sont des données saisies (comme un import Excel), la cible stock est choisie par l'humain (`assertTargetExists`, `:261-276`), et la commande Uber peut être corrigée avant confirmation (`confirm()` accepte un payload corrigé, `:172-174`).

C'est exactement le motif que le GOAL ONB-04 doit reprendre pour `MenuDraft` : écrire un brouillon versionné (`status=draft`) dès l'extraction, jamais l'article/catégorie final, et ne créer/mettre à jour le catalogue réel que via un endpoint d'application séparé déclenché par une confirmation humaine explicite, en appelant les services existants (jamais du SQL direct).

## 6. Gestion d'erreur (IA n'importe quoi / clé absente / quota dépassé)
- **Clé absente** : FAIL-CLOSED avec exception explicite — `OpenAiInvoiceVisionService.php:40-45` et `OpenAiUberTicketVisionService.php:158-163` lèvent `RuntimeException` si `config('services.openai.key')===''`. En pratique le binding (§1) empêche d'atteindre ce code : sans clé, c'est toujours le mock qui est résolu. Testé : `tests/Feature/Purchasing/InvoiceVisionServiceTest.php:116-123` (`test_openai_fails_closed_without_key`).
- **Réponse HTTP non-2xx (couvre 429 quota dépassé)** : pas de détection spécifique du code 429 — traité génériquement par `if (! $response->successful())` → `Log::warning(...)` puis retour `[]` (facture, `OpenAiInvoiceVisionService.php:70-74`) ou `emptyTicket()` (Uber, `OpenAiUberTicketVisionService.php:192-196`). Aucune distinction quota/erreur serveur/timeout dans le code ; tout non-2xx dégrade silencieusement vers « rien lu », jamais une exception qui casserait la requête HTTP entrante.
- **Réponse JSON incohérente / hallucinée** : parsing strictement défensif — `parseResponse()` (facture, `:104-134`) et `normalize()` (Uber, `:228-292`) : `json_decode` invalide → vide ; ligne sans `raw_label`/`title` → ignorée ; champs manquants → `null`/valeurs par défaut, jamais devinés. Le prompt Uber interdit explicitement d'inventer (`OpenAiUberTicketVisionService.php:64-65` : « N'INVENTE RIEN »). Aucun champ IA n'est appliqué tel quel : tout repasse par la validation humaine avant tout effet (§5).
- **Timeout** : `config('services.openai.timeout', 30)` (secondes) appliqué sur le client `Http::` (`OpenAiInvoiceVisionService.php:55`, `OpenAiUberTicketVisionService.php:180`) ; un timeout Guzzle lève une exception réseau que ni l'un ni l'autre service n'attrape explicitement en interne — côté Uber, le contrôleur, lui, entoure l'appel d'un `try/catch(\Throwable)` (`UberPhotoCaptureController.php:103-118`) qui marque la capture `status=failed` sans perdre la trace ; côté facture, `PurchasingScanController::scan()` n'a **pas** ce même try/catch autour de `$vision->extractLines()` (`:88`) — un timeout y remonterait donc en 500 non rattrapé (NON VÉRIFIÉ par un test dédié ; observation de lecture de code seulement, pas reproduite en exécution puisque aucun appel réseau n'a été fait durant cette recon).
