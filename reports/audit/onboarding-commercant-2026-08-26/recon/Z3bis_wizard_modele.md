# Z3bis — Modèle wizard (`ItemWizardProfile`/`ItemWizardStep`) et règles de prix
- Mission : `ONB-03` W1 · lecture seule stricte, aucune écriture DB, aucune modif fichier hors ce rapport.
- Zone gelée respectée : `app/Services/Pricing/PricingService.php` et `public/js/pos-wizard.js` lus uniquement (aucune édition).

## A. Le modèle actuel (5 lignes)
`item_wizard_profiles` (mig. `2026_04_27_143100`, polymorphe depuis `2026_05_05_000020:106-117` CHECK XOR `(item_id IS NOT NULL) <> (item_category_id IS NOT NULL)`) porte `template/version/is_published/branch_id_scope` ; **catégorie gagne sur article** (`ComposerProfileService::resolveForItem` `app/Services/Composer/ComposerProfileService.php:104-118`, teste `showForCategory` avant `showForItem`). `item_wizard_steps` (mig. `2026_04_27_143110:12-36`) porte `step_key, source_type enum(item_attribute,extra_group,addon,fixed), min_select, max_select, allow_repeat, visible_on(json), stockable_choices, position, is_active, addon_role` + CHECK `min_select<=max_select` (l.34) et `position>=0` (l.35) ; modèles `ItemWizardProfile.php:22-25` (scope `WizardProfileBranchScope`), `ItemWizardStep.php:46-53` (revalidation min≤max + addon_role à la sauvegarde). **Aucune colonne de prix.** `price` est explicitement `['prohibited']` — `app/Http/Requests/ComposerStepRequest.php:32` (step isolé) et `app/Http/Requests/ComposerProfileRequest.php:20` (profil) + `:36` (`steps.*.price`). Raison (déduite du code, pas de commentaire explicite trouvé) : le prix reste 100 % SSOT dans `ItemVariation.price` / `ItemExtra.price` / `Item.price` (colonnes lues directement par `PricingService`), jamais dans la config du pas — empêche toute saisie de prix côté composer qui court-circuiterait le SSOT pricing (CLAUDE.md §8).

## B. Comment le supplément payant est exprimé AUJOURD'HUI (sans colonne prix sur le pas)
Motif réel confirmé par grep+lecture : **attribut plafonné à 0 € (variation) + `ItemExtra` payant séparé**, câblé par des commandes idempotentes rejouées en migration.
- `database/migrations/2026_07_28_120000_ensure_wizard_sauce_and_viande_supplement_steps.php` (migration « sauce supplement » demandée) rejoue `EnsureViandeSupplementExtrasCommand`, `EnsureFritesSauceStepCommand`, `EnsureKidsMenuStepsCommand`.
- `app/Console/Commands/EnsureFritesSauceStepCommand.php:121-130` insère les variations sauce à `'price' => 0` (1ʳᵉ sauce gratuite) puis `:159` appelle `EnsureSauceSupplementExtrasCommand::ensure()`.
- `app/Console/Commands/EnsureSauceSupplementExtrasCommand.php:91-101` crée l'`ItemExtra` **« Sauce supplémentaire »** `price=0.50` `group_label='sauce'` — c'est LA migration « sauce supplement » citée par la mission.
- Même motif pour la viande : `app/Console/Commands/EnsureViandeSupplementExtrasCommand.php:106-116` crée l'`ItemExtra` **« Viande supplémentaire »** `price=2.50` `group_label='supplement'|'supplement_bol'`.
- Le nombre d'extras à facturer (N-1 sauces) est calculé **côté client uniquement**, dans le fichier gelé `resources/js/components/frontend/kiosk/KioskWizardComponent.vue:1993-2003` (`extraSauceN = Math.max(0, sauceOrder.length-1)`, boucle qui pousse N fois l'id de l'extra dans `normalizedExtras`). Le backend ne fait que multiplier `price × quantity` reçue (voir D).

## C. Les trois cas métier du commerçant
**(a) « 1ère sauce offerte, suivantes 0,50 € »** — Exprimable AUJOURD'HUI, mais **PAS via un pas de wizard/profil publié**. Montage réel : attribut sauce = variations à `price=0` (choix libre, illimité) + `ItemExtra` « Sauce supplémentaire » (0,50 €) poussé N-1 fois par le JS gelé (`KioskWizardComponent.vue:1993`). Preuve du contournement volontaire : quand un profil composer EST publié, l'étape sauce y est bornée `min_select=1,max_select=1,allow_repeat=0` (vérifié en base, profils publiés id 34/35/36/37/39, ex. step `sauce` id 163) — incompatible avec le multi-sauce. Le docblock `EnsureFritesSauceStepCommand.php:17-33` explique pourquoi : publier un profil composer sur les frites a provoqué une **régression 422** (`assertComposerSelectionsBelongToPublishedProfile`, cf. D) car la caisse envoie toujours la 2ᵉ sauce comme extra générique, non projetable sans case parasite → la commande **dépublie le profil** (`:136-145`) pour que la validation composer soit *skippée*. Conclusion : le modèle de pas n'a **aucune sémantique « inclus N puis payant »** ; ce cas vit entièrement hors composer.

**(b) « viande obligatoire, une seule au choix, sans supplément »** — Exprimable **exactement** aujourd'hui via un pas publié : vérifié en base (`item_wizard_profiles.is_published=1`, ex. profil id 34 = catégorie 1) → step `viande` (`step_id 155`) `source_type=item_attribute, min_select=1, max_select=1, allow_repeat=0`. `PricingService::assertComposerStepConstraints` (l.594-655) fait respecter ce quota (422 si 0 ou >1 sélection). L'absence de supplément n'est PAS une propriété du pas : elle vient du fait que les variations viande sous-jacentes sont à `price=0` dans `item_variations` — si une variation viande avait un `price>0`, le pas la laisserait passer sans broncher (le pas valide un **compte**, jamais un **montant**).

**(c) « boisson en formule +2 € »** — **NON exprimable** comme un delta fixe de +2 €, et **pas via un pas de wizard** du tout. Mécanisme réel trouvé dans le fichier gelé `PricingService.php:793-813` (`menuRoleAdjustedAddonPrice`) : le client tague l'addon `role` (`menu_full|menu_frites|menu_boisson`, valeur envoyée par le client, non dérivée d'un step) et le backend applique un **ratio global** `config('kiosk.menu_pricing')` (`full_ratio=1.0`, `drink_ratio=0.76` — `config/kiosk.php:220,335`) sur `addonItem->price` (l.224-227). Aucune notion de +2 € fixe, aucune granularité par item/catégorie — un seul ratio pour tout le catalogue. `item_addons` n'a **aucune colonne prix** (`DESCRIBE item_addons` vérifié : `id, item_id, addon_item_id, addon_item_variation, role, …` — pas de `price`) : le prix addon = toujours `addonItem.price` (le prix plein de l'item lié), ajusté seulement par ce ratio global.

## D. Calcul ou validation ? (question décisive)
`PricingService` consulte `ItemWizardProfile`/`ItemWizardStep` **UNIQUEMENT pour VALIDER**, jamais pour calculer.
- Appel de garde : `calculateOrder()` ligne **110** → `$this->assertComposerStepConstraints($req)`.
- Le validateur (l.557-657) charge le profil publié, projette les choix (`ComposerProfileProjection::project`), puis vérifie **min/max** (l.614-630), **allow_repeat** (l.632-641), **disponibilité stock** (l.644-653) et **appartenance au profil publié** (`assertComposerSelectionsBelongToPublishedProfile`, l.659) — 100 % booléen/quota, 0 arithmétique de prix.
- Le calcul du prix réel est un bloc **entièrement séparé et antérieur en lecture de données**, qui ne référence jamais `ItemWizardStep` : `itemPrice = $dbItem->price` (l.134), `variationTotal += $dbVar->price × qty` (l.159), `extraTotal += $dbExt->price × qty` (l.189), `unitAddonPrice = menuRoleAdjustedAddonPrice($role, $dbAddon->addonItem->price)` (l.224-227). Ces montants viennent tous des tables `items/item_variations/item_extras/item_addons→items`, jamais de `item_wizard_steps`.
- Conséquence : même si un commerçant configurait un pas avec la sémantique voulue, **rien dans `PricingService` ne saurait aujourd'hui la lire pour en tirer un prix** — il faudrait un nouveau chemin de lecture (colonnes à ajouter, cf. GOAL §6 G-DATA), pas une extension de la logique de validation existante.

## E. Où la règle est dupliquée
1. **DB (SSOT runtime)** : `item_extras.price` = 0.50 (« Sauce supplémentaire ») / 2.50 (« Viande supplémentaire ») — c'est la valeur réellement facturée par `PricingService.php:189`.
2. **Config (seed-time only)** : `config/menu.php:155` `'supplement_sauce_price' => 0.50` — consommé **uniquement** par `database/seeders/MenuSeeder.php:746,764` pour semer l'`ItemExtra` initial ; grep confirme qu'**aucun code applicatif** (`app/`, `resources/`) ne lit cette clé à l'exécution — doublon dormant, dérive possible si quelqu'un change l'un sans l'autre puis reseed.
3. **JavaScript, fichier GELÉ** : `resources/js/components/frontend/kiosk/KioskWizardComponent.vue:1993` recode la **règle** « 1ʳᵉ gratuite, N-1 facturées » (le nombre, pas le prix unitaire — celui-ci est bien lu depuis `item.extras[].price`, data-driven, cf. `resources/js/helpers/kioskPricing.js:39-46`). Donc la valeur numérique (0,50 €) n'est dupliquée qu'en 2 endroits (DB + config seed mort), mais la **RÈGLE MÉTIER** « 1ère incluse, reste payant » n'existe **QUE** dans ce JS gelé — aucune trace côté backend/composer. Idem très probable côté `public/js/pos-wizard.js` (caisse, gelé lui aussi) — non ouvert en détail ce tour-ci (hors scope lecture ciblée composer), mais le docblock `EnsureFritesSauceStepCommand.php:22-23` confirme que la caisse a son propre chemin `hasSauce` data-driven indépendant du composer.

## Réponse compacte (25 lignes)
**Modèle** : `item_wizard_steps` = `min_select/max_select/allow_repeat/visible_on/position/source_type(item_attribute|extra_group|addon|fixed)` — zéro colonne prix ; `price` `['prohibited']` en dur (`ComposerStepRequest.php:32`, `ComposerProfileRequest.php:20,36`). Profil = par item XOR par catégorie (CHECK DB `2026_05_05_000020:106-117`), catégorie prioritaire (`ComposerProfileService.php:104-118`). `fixed` se projette en `[]` (`ComposerProfileProjection.php:176`).

**(a) sauce 1 offerte puis 0,50 €** : PAS via un pas/profil composer. Motif réel = attribut variation `price=0` + `ItemExtra` séparé (`EnsureSauceSupplementExtrasCommand.php:91-101`, 0,50 €), quantité N-1 calculée dans le JS **gelé** `KioskWizardComponent.vue:1993`. Le profil composer publié, quand il existe, borne la sauce à 1 choix strict — incompatible ; il est donc **dépublié** exprès pour ce cas (`EnsureFritesSauceStepCommand.php:136-145`).

**(b) viande obligatoire, 1 choix, sans supplément** : exprimable TEL QUEL aujourd'hui — step publié réel vérifié en base (`profile 34`, step `viande` : `min_select=1,max_select=1,allow_repeat=0`), fait respecter par `PricingService::assertComposerStepConstraints` (422 si violé). L'absence de supplément vient des variations sous-jacentes à `price=0`, pas d'un attribut du pas.

**(c) boisson formule +2 €** : NON exprimable comme delta fixe et hors wizard. Mécanisme réel = ratio global (`config('kiosk.menu_pricing')`, `drink_ratio=0.76`) appliqué au prix plein de l'item-boisson via `role` client-déclaré (`PricingService.php:793-813,224-227`). `item_addons` n'a pas de colonne prix.

**Calcul ou validation** : VALIDATION SEULE. `assertComposerStepConstraints` (`PricingService.php:110,557-657`) ne vérifie que quotas/appartenance/dispo — jamais de montant. Le calcul réel lit `items/item_variations/item_extras/item_addons.price` (l.134,159,189,224-227), sans jamais toucher `item_wizard_steps`.

**Duplication** : (1) `item_extras.price` = SSOT runtime réel ; (2) `config/menu.php:155` = doublon mort (seed-only, lu seulement par `MenuSeeder.php:746,764`) ; (3) la RÈGLE elle-même (pas juste le montant) est codée en dur dans `KioskWizardComponent.vue:1993` (gelé), absente du backend/composer — 3ᵉ lieu, mais niveau « règle », pas « valeur ».
