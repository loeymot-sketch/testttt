### 3.bis — Règle overpayment & rendu monnaie (décision humaine 2026-04-18)

**Principe NF525-compliant** : le rendu monnaie n'est autorisé **que pour les tenders de type `cash`**. Tout autre tender (CB, ticket resto, bon, gift card) exige un paiement strictement égal au reste dû — overpayment rejeté en 422.

**Algorithme de validation `POST /admin/pos-order/{order}/split-payment`** :

```
total_due    = order.total
sum_tenders  = SUM(payments[*].amount)
cash_total   = SUM(payments[cash].amount)
non_cash     = SUM(payments[!cash].amount)

1. non_cash > total_due                     → 422 OverpaymentOnNonCashTender
2. non_cash + cash_total < total_due        → 422 Underpayment
3. non_cash + cash_total == total_due       → PAID (change_returned = 0)
4. non_cash + cash_total > total_due
   AND cash_total > 0
   AND non_cash <= total_due                → PAID (change_returned = sum - total_due)
5. non_cash + cash_total > total_due
   AND cash_total == 0                      → 422 OverpaymentOnNonCashTender (tautologie avec 1)
```

**Persistence** : ligne(s) `order_payments` créées pour chaque tender au montant tendu (pas au montant net après rendu). Une ligne virtuelle `order_payments.method=cash_change amount<0 refund_of_id=<last cash payment>` trace le rendu pour audit.

**AuditLog** action `payment.recorded` avec payload :
```json
{
  "order_id": 123,

```

### Risques POS-9.3

1. **Migration enum MySQL** — l'extension d'un enum column est une opération `ALTER TABLE` potentiellement longue en prod. **Mitigation** : script en mode "add 3 cases" (non destructif) + testé sur staging avant prod + documenté dans `docs/DEPLOY_POS_9_3.md`.
2. **Backfill sur millions de rows** — si la table `orders` a déjà des centaines de milliers de lignes PAID en prod, le backfill peut durer. **Mitigation** : job `php artisan foodking:backfill:order-payments --chunk=1000` batché, relançable.
3. **BROADCAST_MAP front désynchronisé** — si on ajoute `OrderCancelled` mais pas dans `eventContract.js`, le front log "Invalid envelope". **Mitigation** : un seul commit pour les 2 côtés (9.3.6), check CI grep des 2 fichiers.
4. **Conflit LOCK_A sur `EventServiceProvider`** — si Track A ajoute aussi des events Kiosk P9.6. **Mitigation** : coordination via BROADCAST, merge 3-way trivial.
